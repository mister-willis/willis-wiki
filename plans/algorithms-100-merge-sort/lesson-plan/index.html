    Lesson Plan — Merge Sort

    Planbook Fields

    Lesson (Day 1):

    Direct instruction with slides on merge sort: divide the list until every piece is one item (already sorted by definition), then merge sorted pieces back together. The merge operation is demonstrated with two sorted stacks — always take the smaller front item. Lab: students implement and test the merge function first, per the assignment's build order, including uneven lengths and an empty side.

    Lesson (Day 2):

    Brief recap: why a one-item list counts as sorted, and how that ends the recursion. Lab: students implement merge_sort — split, recurse on both halves, merge the results, return — and test the full sorter against odd-length lists, an empty list, and a single item. Scored 0–4 on the rubric printed in the assignment.

    Standards: AP CSP AAP-2.B, AAP-2.M, AAP-2.O, AAP-4.A; AZ CS HS.AP.M.1, HS.AP.M.2

    Learning Objectives

    Students will be able to:

    • Implement merge from its written algorithm: two pointers, compare fronts, drain leftovers.
    • Implement merge_sort as a recursive function with a one-item base case.
    • Explain why merging two sorted lists never requires searching.
    • Test edge cases deliberately: empty, single-item, and odd-length lists.

    Standards Alignment

    Code Standard (abbreviated) Why it's defensible here
    AAP-2.B Represent a step-by-step algorithmic process using sequential code. Both functions are implemented from the assignment's numbered Part 1 and Part 2 algorithms, step for step.
    AAP-2.M Create algorithms; combine and modify existing algorithms. merge_sort is literally a combination: the student's own merge becomes a component of the larger algorithm — build one, then build with it.
    AAP-2.O Write iteration to traverse lists; determine results. The merge loop walks two lists with two positions (i, j) plus leftover-draining — the unit's most demanding traversal.
    AAP-4.A Compare algorithm efficiencies informally. Partial: the lecture compares merge sort's split-and-merge count against one-at-a-time insertion from lab 80 (the discussion is informal counting, not a measured artifact).
    HS.AP.M.1 Decompose problems into components using procedures. The sort decomposes into two procedures with a clean division: merge combines, merge_sort divides.
    HS.AP.M.2 Use combinations of procedures to develop artifacts. merge_sort calling both itself and merge is procedure composition — the artifact exists only through the combination.

    Materials & Setup

    • slides.pptx (this folder) loaded and tested.
    • Python environment; notebooks.
    • Two stacks of numbered index cards, each pre-sorted, for the merge demonstration — merging physically (compare the two visible fronts, take the smaller) teaches Part 2 faster than the slide does.
    • Students should still have last lab's Mondrian in reach: merge_sort's shape is subdivide's shape, and the callback does real work.

    Slides & Direct Instruction

    The deck (8 slides, speaker notes on each) runs: the audacious claim (a sort that refuses to sort) → the three moves: divide, conquer, combine, on the lab's diagram → the merge: two sorted stacks, take the smaller front → merge's algorithm: i, j, and the leftovers → dark slide: this is the Mondrian trick — split, recurse, stop at one → merge_sort's seven steps, with the base case doing all the thinking → your turn: merge two four-item lists by hand, then predict merge_sort([5]) → mission slide. Day 1 stops after the merge-algorithm slide; Day 2 opens on the dark Mondrian-callback slide. Questions worth asking:

    • "Why is a one-item list 'already sorted'?" (nothing to compare — sorted is a claim about pairs, and there are none; this base case ends every recursion)
    • "Why does merging never search?" (both lists arrive sorted, so the smallest unclaimed item is always one of the two fronts — the lab's checkout-lines image)
    • "Where does the actual comparing happen — the splitting or the merging?" (all in the merge; the splits never look at values. Sound familiar? The Mondrian recursion navigated; the base case painted.)

    Pacing — Two 51-Minute Periods

    Day 1

    Minutes Segment What happens
    0–4 Settle + do-now On the board: two sorted lists, [2, 5, 9] and [1, 5, 6]. "Combine them into one sorted list. Watch what your eyes do."
    4–18 Slides Divide-conquer-combine, then the merge demonstrated with the card stacks — narrate the take-the-smaller-front rule until it's boring.
    18–24 Practice Hand-merge slide 7's lists in notebooks, recording which list each item came from. Compare with a neighbor.
    24–46 Lab Implement merge and test it: the do-now's lists, uneven lengths, one empty side. The assignment's tip names these tests.
    46–51 Wrap Cold-close: "Your merge takes two sorted lists. Tomorrow, who supplies them?" (Recursion does — all the way down to lists of one.)

    Day 2

    Minutes Segment What happens
    0–4 Settle + do-now "What does merge_sort([7]) return, and which lines of Part 1 run?" (Just the base case — step 1.)
    4–12 Slides The Mondrian callback and Part 1's seven steps; trace merge_sort([3, 1, 2]) on the board down to the base cases and back up.
    12–44 Lab Implement merge_sort; test odd lengths, empty, single item, and something big and shuffled. Circulate for missing returns — the lab's warning callout is the day's most-hit bug.
    44–51 Wrap Cold-close: one student traces where [4, 2] gets compared (in merge, not in the splits). Preview: "Every algorithm so far had a right answer waiting. Next lab meets a problem that outlasts the universe."

    ELEOT: The 20-Minute Window

    Item The move in this lesson
    B.2 The build order (merge first, then merge_sort) turns a famously hard algorithm into two climbable steps with a test between them.
    B.4 Tracing the recursion and locating where comparison happens are analysis; the hand-merge grounds it.
    B.5 Both days run on the assignment's numbered algorithms and tips; students self-direct through the build order.
    C.3 The assignment's collapsed test-hint and warning callout are self-rescue rails; the do-now's hand merge is the reference when code confuses.
    D.1 The neighbor comparison of hand-merges and the wrap traces are structured exchanges about mechanism, not answers.
    D.2 Say the real-world line: this is (with refinements) how Python's own sorted() and big-data pipelines actually sort — students are implementing production ancestry.
    D.3 Both days center sustained implementation with self-run tests.
    E.1 Rotating check-ins: a passing merge is the Day 1 gate; the edge-case tests are Day 2's evidence.
    E.3 The Day 2 do-now and wrap have students verbalizing the recursion's behavior, not just running it.
    E.4 The rubric's 4 requires tests visible in the file — including odd, empty, single — name it during rotation so testing isn't an afterthought.
    G.2 Original implementation of a canonical algorithm, tested by the student.

    Common Student Errors

    • Missing return — in merge_sort's base case, its final step, or merge itself. The program runs fine and sorts nothing; the lab's warning callout names this as the signature bug.
    • Forgetting the leftover-draining steps (Part 2, steps 4–5) — merges lose the tail of whichever list runs longer; odd-length tests exist to catch it.
    • Advancing the wrong pointer after a comparison, or advancing both — duplicated or skipped items that only show up with duplicate values in the test data (note 5 appears in both suggested test lists; that's not an accident).
    • Splitting with [:middle] on both halves instead of [:middle] and [middle:] — infinite recursion on lists of two.
    • Testing only the happy path. The rubric pays for empty, single, and odd-length evidence in the file.

    Assessment & Evidence

    • Deliverable: the .py file with merge and merge_sort (see Turn It In).
    • Score: 0–4 holistic rubric in the assignment. A 4 has both functions correct, returning (not printing) results, with tests visible in the file including odd-length, empty, and single-item lists.
    • Look-fors during check-ins: merge tested before merge_sort was started; a return on every path; test calls at the bottom of the file that match the rubric's list.
