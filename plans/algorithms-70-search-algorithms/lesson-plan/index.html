    Lesson Plan — Search Algorithms

    Planbook Fields

    Lesson (Day 1):

    Direct instruction with slides on the two classic search algorithms: linear search (check everything, front to back) and binary search (halve the sorted list every guess), with the number-guessing demonstration and an iteration-count comparison. Lab: students extract the linear search algorithm from given code into numbered natural language in their project notebooks.

    Lesson (Day 2):

    Brief recap: the halving demonstration replayed on a list on the board. Lab: students implement binary search in Python from the given natural-language algorithm, report when the target is missing, and test four cases — first item, last item, middle item, missing item. Scored 0–4 on the rubric printed in the assignment.

    Standards: AP CSP AAP-2.O, AAP-2.P, AAP-4.A, AAP-2.B; AZ CS HS.AP.C.1

    Learning Objectives

    Students will be able to:

    • Extract linear search's algorithm from code into precise natural language.
    • Implement binary search from a written algorithm, including the not-found case.
    • Count iterations for each search on the same list and compare growth.
    • State binary search's precondition and what breaks without it.

    Standards Alignment

    Code Standard (abbreviated) Why it's defensible here
    AAP-2.O Write iteration to traverse a list; determine results of traversals. Linear search is the canonical full traversal — students trace it, describe it, and count its steps.
    AAP-2.P Binary search: determine iterations required; data must be sorted. The Day 2 build is the standard verbatim, including the sorted-data precondition the lab warns about in its own callout.
    AAP-4.A Determine algorithm efficiency; compare algorithms informally by counting executions. The lecture's worked comparison — steps for 7, 100, and 1,000,000 items under each search — is the standard's informal-measurement method, applied.
    AAP-2.B Represent a step-by-step algorithmic process using sequential code. Day 2 translates a given numbered algorithm into working Python, step for step.
    HS.AP.C.1 Justify control structures; explain benefits and drawbacks of choices. Partial: the while low <= high loop is justified against a for loop (unknown iteration count), and the linear-versus-binary tradeoff (no precondition versus speed) is discussed — justification happens in discussion more than in a written artifact.

    Materials & Setup

    • slides.pptx (this folder) loaded and tested.
    • Notebooks (Day 1 deliverable) and Python environment (Day 2).
    • A guessing-game plant: pick a number 1–100, have the class binary-search it aloud. Seven guesses maximum, every time — that demonstration carries the whole lesson.
    • Optional but effective: a physical phone book or dictionary. Half the room has never opened one.

    Slides & Direct Instruction

    The deck (8 slides, speaker notes on each) runs: the phone-book problem (page one versus the middle) → linear search: the code, traced → the guessing game: 1 to 100 in seven guesses → binary search's move: halve, compare, discard → dark slide: a million checks versus 20 — the count that changes everything → the precondition: sorted or nothing → your turn: trace binary search for 18 in the board list, counting comparisons → mission slide. Day 1 stops after the guessing-game and linear-search slides; Day 2 opens on the halving-move slide. Questions worth asking:

    • "Why can't binary search work on an unsorted list?" (discarding half only works if you know which half is wrong — sorted order is the knowledge)
    • "A million items. How many halvings until one remains?" (about 20 — have them halve on the board until belief sets in)
    • "When is linear search the right choice?" (unsorted data, tiny lists, or when you'll search once — sorting first costs more than it saves)

    Pacing — Two 51-Minute Periods

    Day 1

    Minutes Segment What happens
    0–4 Settle + do-now On the board: "Find 42's position in this 7-item list. How many looks did you need? What if the list had a million items?"
    4–18 Slides Linear search traced, then the live guessing game — class versus 1-to-100, counting guesses aloud.
    18–24 Discussion Why did seven guesses suffice? Extract the halving idea from the class's own play before naming it.
    24–46 Lab Extract the linear search algorithm into numbered natural language. The robot test applies: someone who never saw the code could rewrite it.
    46–51 Wrap Cold-close: one extraction read aloud; class hunts ambiguity. Preview: "Tomorrow you build the seven-guess machine — from words we hand you."

    Day 2

    Minutes Segment What happens
    0–4 Settle + do-now "Binary search for 25 in [3, 7, 9, 12, 18, 25, 42]. Write the sequence of middle values you'd check."
    4–14 Slides The binary search algorithm walked step by step; map low/high/middle to Python; the sorted-list warning gets its minute.
    14–44 Lab Implement from the given algorithm; test first, last, middle, missing. Circulate for the low <= high condition and the missing-item report.
    44–51 Wrap Tally the four test cases on the board. Cold-close: "Binary search demanded a sorted list. Where do sorted lists come from?" Nobody knows. Preview: "Exactly. Next lab."

    ELEOT: The 20-Minute Window

    Item The move in this lesson
    B.2 The guessing game makes the hard idea (logarithmic halving) playable before it's formal; the implementation has a numbered algorithm as guardrails.
    B.4 Counting comparisons and arguing why sorted order is load-bearing are analysis, not recall.
    B.5 Day 2's build runs on the assignment's written algorithm — students self-direct from the document, per the course's habit.
    C.3 The assignment's hint (the while loop, break on success) is the sanctioned self-rescue; neighbors compare extractions after both are written.
    D.1 The guessing game and the halving debrief are whole-class exchanges where learner reasoning does the work.
    D.2 Phone books, dictionaries, and "why your contacts app finds names instantly" tie both algorithms to lived experience.
    D.3 Both days are majority hands-on: extraction writing, then implementation and testing.
    E.1 Rotating notebook check-ins: the extraction Day 1, the four-case test evidence Day 2.
    E.3 The Day 2 do-now has students verbalizing the middle-value sequence before touching code — understanding shown, then applied.
    E.4 The rubric's 4 requires evidence of all four test cases; name that during rotation so students test to the standard.
    G.2 Original Python implementation of a classic algorithm, tested by the student.

    Common Student Errors

    • while low < high instead of low <= high — the last unexamined item is exactly where the target hides in the first/last tests. This is why the test matrix exists.
    • Updating to middle instead of middle ± 1 — the loop never shrinks past the middle and runs forever on missing targets.
    • Testing with an unsorted list and reporting the algorithm "broken." The lab's warning callout covers it; ask what step 1 of the algorithm says.
    • Printing "not found" inside the loop (fires every non-matching pass) instead of after it ends.
    • Extractions that describe the example ("look for 18") instead of the algorithm ("look for the target") — parameters, not constants.

    Assessment & Evidence

    • Deliverable: the linear search algorithm in the notebook, and the tested binary search .py file (see Turn It In).
    • Score: 0–4 holistic rubric in the assignment. A 4 requires an accurate extraction plus an implementation that reports missing targets and shows all four test cases.
    • Look-fors during check-ins: numbered extraction steps free of code; low, high, middle updating correctly in a hand-trace; four test runs visible (first, last, middle, missing) rather than one lucky hit.
